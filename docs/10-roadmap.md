## 当前已交付（摘要）

- Center + Agent，Python 3 标准库；SQLite 存储；中文监测台 + 客户端部署页
- 采集：系统资源 + 加速卡（英伟达 / 华为昇腾 / 寒武纪 / 瑞芯微 RKNN）
- 主机类型：`auto` | `cpu` | `gpu`
- 异常阈值着色；主机详情 **时间段统计**（1h/2h/6h/24h/7d）+ 趋势图
- 部署：Excel/CSV 导入、SSH（密码需中心机 `sshpass`，或私钥）、配置地址自动探查；Agent 默认目录 `/opt/monitor-agent`（Center 仍为 `/opt/monitor`）
- 本地守护：`scripts/local_up.sh` / `local_down.sh`

## 下一步待办

### N1. 测试部署到服务器使用 — `todo`

**目标**：在真实机房/云主机完成「中心机 + 至少 1～N 台 Agent」闭环验收。

**建议步骤**

1. 选一台中心机执行 `./scripts/deploy_center.sh --port 8080`（或网页部署前先装好中心）
2. 打开 `http://<中心局域网IP>:8080/deploy.html`，确认「中心对外访问地址」为可达 IP（勿用 `127.0.0.1`）
3. 用密码或全局私钥添加目标机；点「测试连通/部署条件」后再部署
4. 监测台确认主机在线、详情统计与趋势有数据；抽测 Excel 批量导入

**验收要点**：跨机上报、SSH 部署成功/失败信息可读、进程重启后自启（systemd 或守护）、Token（若启用）生效。

**依赖**：只走中心「客户端部署」或中心机 `deploy_fleet.sh`；目标机 SSH 可达；防火墙放行中心端口；密码登录需中心机 `sshpass`；非 root 勿用 `/opt/monitor-agent`。

---

### N2. 框架化：指标可扩展，采集变更尽量不牵动其余代码 — `todo`

**目标**：后续新增/调整检测指标时，**优先只改采集实现**（Agent 侧采集模块或脚本），中心存储、API、前端尽量通过约定自动适配，避免到处改字段。

**设计方向（待落地）**

| 层次 | 约定 |
| --- | --- |
| 采集 | 指标以「命名空间 + 键」上报（如 `system.cpu_percent`、`accel.*.util_percent`）；新指标只在 `agent/metrics/*` 增加采集器并注册 |
| 报文 | 允许 `metrics` 字典或保留结构化块；未知字段透传入库，中心不强依赖固定列 |
| 存储 | 历史可存「通用 KV / JSON 快照」；列表/统计用可配置的「展示清单」而非硬编码 |
| 展示 / 判定 | 前端与 `anomaly` 阈值从配置表驱动（指标名 → 标签、单位、阈值），而不是写死在 `app.js` |

**非目标（本阶段）**：完整插件市场、动态热加载第三方 so；先做到「改采集 + 改一份指标清单配置」即可上线新指标。

**验收**：新增一个示例指标（如某厂商温度字段）时，除采集模块与指标清单配置外，无需改 `storage`/`api`/`app.js` 业务逻辑（或仅极少胶水）。

---

### N3. 拓扑/扩补图类界面：可视化全量链接信息 — `todo`

**目标**：类似网络拓扑 / 扩补图，展示监控域内 **主机与关联地址（指定机器、中心、探测结果）** 的连接关系与可达状态。

**输入数据（已有可复用）**

- 部署清单：`ip`、`host_id`、`peer_hosts`
- 自动探查结果：可达 / RTT / SSH
- 监测台：主机在线与异常状态

**界面设想**

- 节点：中心、客户端、关联机器（peer）
- 边：上报链路（Agent→Center）、关联探查、SSH 部署关系
- 交互：点选节点看详情；按不通/偏高过滤；可导出关系清单

**验收**：一屏可读全量链接；状态与探查结果一致；机器数增多时仍可缩放/分层浏览。

---

### N4. 技术验证：当前实现适合同时监控多少机器 — `todo`

**目标**：给出可复现的容量结论（不是拍脑袋），指导生产规模与是否需要拆分/换存储。

**建议压测口径**

| 维度 | 方法 |
| --- | --- |
| 上报压力 | 用脚本模拟 N 个 Agent，间隔 15s POST `/api/v1/metrics` |
| 中心资源 | 观察 CPU、内存、SQLite 库体积、`metrics_history` 行数、写入延迟 |
| 读路径 | 列表 `/hosts`、详情 `period-stats`、history、监测台 15s 轮询 |
| 变量 | N ∈ {50, 100, 200, 500, …}；保留天数 7；是否开启部署库同机 |

**产出物**：`docs/` 下容量验证短报告（推荐配置、临界现象、优化建议：批量写、降采样、分库等）。

**初步预期（待验证）**：单进程 + SQLite 推送模型，小中规模（数十～低百台）更稳妥；更高密度需专项优化或架构升级。

---

## 优先级建议

1. **N1** 服务器实装（立刻产生业务价值、暴露真实问题）  
2. **N4** 容量摸底（决定能否扩面）  
3. **N2** 框架化（降低后续加指标成本）  
4. **N3** 拓扑可视化（体验增强，依赖部署/探查数据稳定）
