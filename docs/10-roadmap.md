## 当前已交付（摘要）

- Center + Agent，Python 3 标准库；SQLite 存储；中文监测台 + 客户端部署页
- 采集：系统资源 + 多挂载磁盘 `disks[]` + 加速卡（英伟达 / AMD / 华为昇腾 / 寒武纪 / 瑞芯微 RKNN），列表用 `accel_summary`。没有厂商工具时从 PCI sysfs 报出已知卡，健康为 abnormal，利用率不当成 0% 样本。寒武纪文本按整行 `Card N` 解析（MLU370 / MLU270），`Good` 不报健康告警。主机清单来自最近一次上报，下一包会换成新的卡数
- 主机类型：`auto` | `cpu` | `gpu`
- 监测台三页签：实时监控（排序、完整 IP、资源组、负责人/用途、规格与利用率分列、离线不展示实时数字、隐藏/导入资产）、时段统计、使用诊断（日/周/月报告入库；中心按时生成，错过不补；排行和闲忙带负责人/用途）
- `retention_days` 可配。展示地址优先手工地址 / 未停用清单 / host_id，跳过 `198.18.0.0/15`。同机改址保留 host_id 和历史上报，旧 IP 进历史，旧部署目标停用；apply 时记下可撤销状态。`previous_ips: []` 可清空历史 IP，部署目标可用 `retired` 恢复
- Agent 下限仍是 3.6。没有合适解释器时使用中心上的便携 CPython。中心升级走 `scripts/push_upgrade.sh` / `scripts/upgrade_center.sh`：先从单元套用 `LD_LIBRARY_PATH`/`PATH` 再测新包，通过才同步；回滚不动 `data/`。预同步测试在沙箱里跑（假 systemctl、临时 HOME），不会停掉现场的 `monitor-agent`。`--check-only` 只上传到 `/tmp` 并做同步前测试和磁盘预检。不喂数据的 ssh 使用 `ssh -n`，预同步测试的 stdin 接到 `/dev/null`。便携包用 `scripts/push_python_bundles.sh` 放到中心（远端目录不存在也会创建）
- 部署：只走 `/deploy.html` 或中心机 `deploy_fleet.sh` / `deploy_agent.sh`。Excel/CSV 导入；密码登录需要**中心机**的 `sshpass`（或改用私钥）。Agent 默认 `/opt/monitor-agent`，Center 默认 `/opt/monitor`。笔记本 sshpass/scp 装 Agent 已废弃
- 本地守护：`scripts/local_up.sh` / `local_down.sh`
- v1.10.0 已开始做体验，不新增监测能力：监测台和部署页共用顶栏（总览 / 主机 / 诊断 / 运维）；实时页有「今日关注」（离线、磁盘快满、卡异常、高负载）；加速卡健康列和异常说明用人话，原始 `health` 仍留在数据里；诊断报告里的主机行可点进主机详情（`#host=`）。长期空闲清单、把部署页收进同一页、中心升级引导界面都还没做

## 下一步待办

### N1. 测试部署到服务器使用 — `todo`

**目标**：在真实机房/云主机完成「中心机 + 至少 1～N 台 Agent」闭环验收。

**建议步骤**

1. 选一台中心机执行 `./scripts/deploy_center.sh --port 8080`（或网页部署前先装好中心）
2. 打开 `http://<中心局域网IP>:8080/deploy.html`，确认「中心对外访问地址」为可达 IP（勿用 `127.0.0.1`）
3. 用密码或全局私钥添加目标机；点「测试连通/部署条件」后再部署
4. 监测台确认主机在线、详情统计与趋势有数据；抽测 Excel 批量导入

**验收要点**：跨机上报、SSH 部署成功/失败信息可读、进程重启后自启（systemd 或守护）、Token（若启用）生效。

**依赖**：只走中心「客户端部署」或中心机 `deploy_fleet.sh`；目标机 SSH 可达；防火墙放行中心端口；密码登录需中心机 `sshpass`（不要在笔记本上另做 scp 安装）；非 root 写 `/opt/monitor-agent` 时走产品路径里的 sudo。

### N2. 框架化：指标可扩展，采集变更尽量不牵动其余代码 — `todo`

**目标**：后续新增/调整检测指标时，**优先只改采集实现**（Agent 侧采集模块或脚本），中心存储、API、前端尽量通过约定自动适配，避免到处改字段。

**设计方向（待落地）**

| 层次 | 约定 |
| --- | --- |
| 采集 | 指标以「命名空间 + 键」上报（如 `system.cpu_percent`、`accel.*.util_percent`）；新指标只在 `agent/metrics/*` 增加采集器并注册 |
| 报文 | 允许 `metrics` 字典或保留结构化块；未知字段透传入库，中心不强依赖固定列 |
| 存储 | 历史可存「通用 KV / JSON 快照」；列表/统计用可配置的「展示清单」而非硬编码 |
| 展示 / 判定 | 前端与 `anomaly` 阈值从配置表驱动（指标名 → 标签、单位、阈值），而不是写死在 `app.js` |

**非目标（本阶段）**：完整插件市场、动态热加载第三方 so；先做到「改采集 + 改一份指标清单配置」即可上线新指标。

**验收**：新增一个示例指标（如某厂商温度字段）时，除采集模块与指标清单配置外，无需改 `storage`/`api`/`app.js` 业务逻辑（或仅极少胶水）。

### N4. 技术验证：当前实现适合同时监控多少机器 — `todo`

**目标**：给出可复现的容量结论（不是拍脑袋），指导生产规模与是否需要拆分/换存储。

**方法已经有，数字还没有。** `scripts/capacity_probe.py` 用现有上报入口往临时库写合成点，按主机数、采样间隔、`retention_days` 外推历史上报行数和库体积。怎么跑、怎么读、空白结果表见 `docs/15-capacity-lab.md`。冒烟只证明命令能结束。跑完之前不要在文档里写主机上限。

**建议压测口径**

| 维度 | 方法 |
| --- | --- |
| 上报压力 | `capacity_probe.py --hosts N --interval 15`（走 `POST /api/v1/metrics` 的同一入口；`--http` 时经本机 HTTP） |
| 中心资源 | 探针打印库体积、`metrics_history` 行数、写入 p50/p95。CPU 和内存看运行探针的那台机器，不由探针编造 |
| 读路径 | 同一次运行里计时主机列表、单机 history、单机与集群 `period-stats` |
| 变量 | 主机数、采样间隔、`retention_days`、每台实际写入条数。保留期全量行数是外推，不是默认写满 |

**产出物**：把一次正式运行的数字填进 `docs/15-capacity-lab.md` 的结果表。表在实测前保持空白。

**初步预期（待验证，不是结论）**：单进程 + SQLite 推送模型，小中规模可能更稳妥。这句话在结果表填上之前不能当成推荐配置。双中心不在 N4 里做。

## 用户流程 / 体验

功能已经够用（v1.9.5 起）。下一阶段不新增监测能力，而是把常见任务做顺：信息架构和任务流。架构仍是轻量 Center + Agent、Python 标准库，不引入 Prometheus / Grafana。改的是壳、状态说法、深链和运维入口，不是存储或采集重做。

### 问题（使用者视角）

- 控制台是拆开的：实时 / 时段 / 诊断在 `index.html`，Agent 部署在单独的 `/deploy.html`，中心升级只在工作站脚本 `scripts/push_upgrade.sh`。办完一件事要在几个界面之间跳。
- 「今天该管什么」要把异常条、主机表和诊断报告拼起来看。
- 状态说法偏技术（`Health=abnormal`、原始短码），而不是白话结果（驱动缺失、磁盘快满、离线）。
- 报告里主机只是文字，没有链回主机详情。

### 目标信息架构

同一套壳，四个入口：

| 入口 | 做什么 |
| --- | --- |
| **总览** | 打开就看到关注清单：离线、磁盘 ≥95%、卡异常、高负载、长期空闲 |
| **主机** | 查找和编辑资产，隐藏、更换地址 |
| **诊断** | 日 / 周 / 月报告；主机行可点进主机详情 |
| **运维** | Agent 部署和中心版本 / 升级引导放在同一处（同一条任务） |

v1.10.0 先把四个入口放到同一顶栏。部署仍是 `/deploy.html`，时段统计仍是监测台里的页签。把部署收进同一页、以及中心升级引导，归 U2。

### U1. 总览与可读状态（体验最大）— `doing`

**目标**：打开监测台就能回答「今天该管什么」，状态用人话，异常和报告能点回主机。

**范围**

- 「今日关注」：离线、磁盘临界（沿用 `disk_critical_percent`，默认 ≥95%）、卡异常、高负载的数量，点一下筛到主机表。高负载只用现有异常判定（CPU 达到异常线，或 load1/核数、load5/核数达到现有负载阈值 `cpu_load_per_core_warn`，默认 2.0），不另做报告引擎
- 长期空闲仍看使用诊断里的「基本不用」。它要历史样本，不在这一刀里新算
- 白话状态，与采集 note 对齐：驱动缺失、工具不在 PATH、硬件异常 / 设备无响应。原始 `health` 留在数据里
- 深链：报告里的主机行、异常 / 离线行 → 主机详情（`#host=`）
- 监测和运维共用顶栏，不再像两个站点

**验收**

- 打开实时页能读出上述四类的数量，点类别就只看这类主机，不必先拼异常条和主机表
- 卡异常等人看的字是中文结果，不再只剩 `Health=abnormal`
- 诊断报告里的主机行可点进该主机详情
- 监测台与 `/deploy.html` 顶栏都是总览 / 主机 / 诊断 / 运维

**本版尚未完成**：总览里的长期空闲名单；部署页并入同一页（U2）。

**范围**

- 部署页收进同一套壳（不再是感觉上的另一个站）
- 从离线或异常主机发起部署时，目标已选中，仍只走 `/deploy` 与中心机 `deploy_fleet.sh` / `deploy_agent.sh`

- 运维里能看到中心版本，并写清先 `--check-only`、通过后再正式升级。界面不提供第二条升级通道

## 长期运维 / 总运维

监测要跑很多年。下面这些是反复发生的运维成本，不是新的监控功能。小修可以跟 U1 同一轮；需要新产品界面或新通道的仍标 `todo`。

### O1. 升级与回滚卫生 — `doing`

**不变量**（已经是产品路径，界面和脚本都不许另开旁路）：

- 升级只走 `scripts/push_upgrade.sh` → `scripts/upgrade_center.sh`。先 `--check-only`，通过后再正式升级。`scripts/lib/sync_tree.sh` 是函数库，直接执行不会升级
- 永远保留 `config/center.json`、`data/`、`vendor/` 里已放置的便携包，以及 systemd 单元里已有的 `Environment=`
- 回滚只恢复代码和单元，不覆盖 `data/`

**本版已做**

- 清理旧备份时同时认两种目录名：`<安装名>-backup-YYYYMMDDHHMMSS` 和 `<安装名>-backup-YYYYMMDD-HHMMSS`（可带 `-pid`）。按时间从旧到新删，不再按字典序把带横线的较新备份先删掉
- Agent 上报的 `agent_version` 改读 `agent.__version__`，与当前发布号一致（v1.10.0）。中心版本仍是 `center.__version__`，`/api/v1/health` 已返回

**仍待做**

- 运维页上稳定看到中心版本、Agent 版本和最近备份（展示，不在浏览器里执行升级）——与 U2 一起做
- 单独备份和恢复已经有脚本（`scripts/backup_center.sh`、`scripts/restore_center.sh`），说明在 `docs/14-ops-runbook.md`。升级失败时的自动回滚仍然只恢复代码和单元，不覆盖 `data/`。连数据库一起退回必须人执行 `--with-data`

**验收**：两种备份目录名混在一起时，留下的是较新的；`center.json` / `data/` / 便携包 / 单元 Environment 在正式升级后仍在。

### O2. 机群生命周期 — `todo`

**目标**：机器离线、改址、停用、隐藏，都有固定走法，不在主机上留探查垃圾。

**范围**

- 离线恢复：先看见（U1 今日关注）→ 再看能不能连上 → 再部署。部署只走 `/deploy` 产品路径
- 隐藏和彻底删除分开：隐藏可恢复；硬删要确认，并说明历史会一起去掉
- 同机改址和撤销、部署目标 `retired`，沿用现有行为，不另写一套
- 探查和厂商工具不在目标机工作目录留下文件（例如 `cnmon_info.json` 只在临时目录）

**验收**：一台离线主机可以从总览走到部署；隐藏的机器不会被探查文件或另一次安装路径“装回来”。

### O3. 数据与容量 — `todo`

**目标**：库和报告不会在没人看的时候慢慢把磁盘吃满，也不会把中心或 Agent 宕机造成的空洞当成“这台机器很闲”。

**范围**

- `retention_days` 只清历史上报，已生成的诊断报告另算保留
- SQLite 体积、`metrics_history` 行数怎么看，写进容量说明（探针输出和 `docs/15-capacity-lab.md`）
- 容量数字以 **N4** 的实测结果表为准，不在这里猜台数。方法已经有，表还是空的
- 中心或 Agent 停机时，报告和时段统计要能看出样本断档，而不是静默当成低利用率

**验收**：保留期和报告保留的差别写在一处；停机窗口不会被说成“基本不用”。

### O7. 测试夹具卫生 — `done`

提交进仓库的加速卡样例只用占位序列号 / UUID（`GPU-00000000-0000-4000-8000-…` 一类）。真实序列号不得作为“不该出现”的秘密留在夹具里。`tests/test_accel_fixtures.py` 会扫这些占位。

## 优先级建议

一条线，不是三张互不相干的清单。U 是把任务做顺，O 是多年跑下去的成本，N 是实装、容量和扩展。体验项不取消 N。

**现在**

1. **U1** 总览与可读状态（本轮实现。v1.10.0 已交付顶栏、今日关注四类、白话健康、报告深链；长期空闲名单仍待）
2. 跟 U1 同一轮、改动小的运维卫生：备份目录两种名字的清理顺序、Agent 版本串跟发布号、Mac 同步不把 `._*` 推进 `vendor/`（O1 / O4 里已做的部分）。夹具占位（O7）保持

**接着**

3. **U2** 运维闭环（部署收进同一壳；升级只引导 `push_upgrade.sh --check-only` 再正式升级）
4. **O6** 中心自身可观测、**O2** 离线恢复这条任务走完、**O3** 保留期和断档（O3 的数字等 **N4**）
5. **U3** 可选：保存筛选（含长期空闲）、管理 API Token（O5）。报告推送明确后置，不进这一轮

**仍保留的实装与能力（不因体验项删掉）**

1. **N1** 服务器实装（真实环境闭环，暴露 U / O 在纸面上看不到的问题）
2. **N4** 容量摸底（探针见 `docs/15-capacity-lab.md`；O3 只引用填好的结果表，不引用冒烟数字）
3. **N2** 框架化（降低以后加指标的成本）
4. **N3** 拓扑可视化（依赖部署和探查稳定之后）
